The 5 Microsoft 365 security settings Swiss SMBs almost always have wrong

Over the last few years I have looked inside a lot of Swiss SMB tenants. The same five things are wrong in nearly all of them — and none take more than an afternoon to fix. Here is how to check your own in about twenty minutes.

When a Swiss business asks me to look at their Microsoft 365 tenant, I don't start with a 200-point audit. I start with five settings. They are not exotic, they are not expensive to fix, and in my experience they are misconfigured in roughly four out of five small-business tenants — usually because the tenant was set up years ago by someone in a hurry and nobody has looked since.

This is the self-audit version. You need a Global Administrator login and about twenty minutes. For each item I explain what I typically find, why it matters for a Swiss business in particular, how to check, and what the fix looks like.

1. MFA is "on" but not actually enforced

What I find: the owner is certain MFA is enabled. It is — for the three people who set it up themselves when prompted. Everyone else is still on password only, and legacy authentication protocols (IMAP, POP, SMTP AUTH, older Office clients) are still allowed, which bypasses MFA entirely even for the users who have it.

Why it matters: password-spray and credential-stuffing attacks against Microsoft 365 are constant and automated. Enforced MFA stops the vast majority of them. Under the nDSG you are expected to apply security measures appropriate to the risk; unenforced MFA is hard to defend as appropriate.

How to check

Entra admin centre → Protection → Authentication methods → User registration details: look at the "MFA registered" column. Then Entra admin centre → Protection → Conditional Access: is there a policy that requires MFA for all users, and one that blocks legacy authentication? If the list is empty, nothing is enforced. If you have no Entra ID P1 (Business Basic/Standard), check Properties → Manage security defaults instead.

The fix

With Business Premium or E3/E5: create two Conditional Access policies from Microsoft's templates — "Require MFA for all users" and "Block legacy authentication" — run them in report-only mode for a week, then switch them on. Without P1: turn on Security Defaults. Either way, exclude one documented break-glass account (see point 2).

2. Everyone who ever needed something is a Global Administrator

What I find: six Global Admins in a fifteen-person company. The owner, the bookkeeper, a former IT supplier, an ex-employee whose account was never disabled, and a shared "info@" mailbox that someone made an admin to fix a calendar problem in 2021. All of them use their admin account for daily email.

Why it matters: an admin who reads email with a Global Admin account turns one phishing click into a full tenant compromise — every mailbox, every file, every setting. And if the only admin is one person and that person is locked out, so is the company.

How to check

Entra admin centre → Roles & admins → Global Administrator. Count the members. Then check whether each one also has a mailbox and licences assigned (they shouldn't).

The fix

Two to four Global Admins maximum. Give each of them a separate, unlicensed admin account with no mailbox (for example adm-paul@) and keep their normal account as a plain user. Create one break-glass account with a very long password stored offline, excluded from Conditional Access, and alerted on when it signs in. Remove everyone else — most of them only need Exchange Administrator or Helpdesk Administrator, if anything.

3. "Anyone with the link" sharing is still the default

What I find: SharePoint and OneDrive external sharing left at the Microsoft default of "Anyone", meaning every user can create links that work for anybody on the internet, forever, with no sign-in. Nobody knows how many of those links exist. Usually quite a few.

Why it matters: this is the most common way client data leaves Swiss companies, and it never shows up in a security log because nothing was "breached" — someone shared a folder with a supplier in 2023 and the link still works. For personal data this is exactly the uncontrolled disclosure the nDSG makes you responsible for.

How to check

SharePoint admin centre → Policies → Sharing. If the SharePoint and OneDrive sliders sit at "Anyone", that is the finding. Also look at whether anonymous links have an expiry.

The fix

Set the organisation level to "New and existing guests" (recipients must sign in or verify a code). If you genuinely need anonymous links for a specific site, allow them for that site only and force a 30-day expiry and view-only permission. Then run a sharing report to find and review the existing anonymous links.

4. Nobody is told when a mailbox starts forwarding email to Gmail

What I find: no alert policies beyond the defaults, auto-forwarding to external addresses permitted, and the unified audit log either switched off or never looked at.

Why it matters: when an attacker gets into a mailbox, their first move is almost always a hidden inbox rule that forwards or deletes mail — typically the invoices — so they can quietly redirect a payment weeks later. In Switzerland this is the single most common path to actual financial loss I see. The second move is sending phishing to all your contacts from your own domain; your clients' trust in your email is at stake.

How to check

Exchange admin centre → Mail flow → Remote domains → Default: is "Allow automatic forwarding" on? Defender portal → Policies → Alert policy: is there anything beyond the Microsoft defaults, and does it send to a mailbox someone reads? Purview → Audit: does a search return results at all?

The fix

Block external auto-forwarding in the outbound anti-spam policy. Make sure audit logging is on. Create three alert policies that go to a mailbox a human reads: creation of inbox forwarding rules, elevation of a user to an admin role, and (if you have P1/P2) risky sign-ins. Takes about half an hour.

5. "Microsoft backs it up" — and it doesn't

What I find: no backup of Microsoft 365 at all. When I ask, the answer is that it's "in the cloud". What actually exists is Microsoft's retention: deleted items recoverable for 30 days, deleted SharePoint files for 93 days, and after that, nothing. No protection against ransomware that encrypts synced OneDrive files, a disgruntled leaver who empties a mailbox, or a well-meaning colleague who deletes the wrong library.

Why it matters: Microsoft's own service agreement tells you to back up your data with a third party. For a Swiss business the nDSG adds a second angle: you are responsible for the availability and integrity of the personal data you hold, and "we assumed Microsoft had it" is not a defence.

How to check

Ask yourself one question: if every file in SharePoint were encrypted tonight, how would you get yesterday's copy back? If the answer involves hoping, you have no backup.

The fix

Add a dedicated Microsoft 365 backup covering Exchange, SharePoint, OneDrive and Teams, stored outside Microsoft — ideally in Switzerland (I use Infomaniak's Swiss storage for this). Then do the thing almost nobody does: test a restore, once a quarter, and write down that you did.

The honest summary

None of these five fixes needs new software beyond the backup, and most of them are included in the Business Premium licence many Swiss firms already pay for without using. If you fixed all five this month you would be ahead of most companies your size in Switzerland.
